Prepared for Reach Capital · Technical overview

A faculty-signed answer pipeline for AI in lifestyle medicine.

Palonur is a verification pipeline that routes a user's lifestyle-medicine question through a Stanford-curated corpus, forces the model into a structured output, runs a citation guard against what was actually retrieved, and routes anything new to the named faculty steward for approval before it ships. Sleep is live, with Prof. Jamie Zeitzer's name on every answer; six more pillars are queued behind the same pipeline.

How it works — request lifecycle, end to end

1Question in. Consumer and partner traffic both hit POST /api/sleep-agent over SSE; the route is wrapped in partnerKeyMiddleware("sleep-agent"), which validates the partner API key and enforces per-key rate and concurrency limits. A lighter /api/agent/query endpoint (per-IP limiter, 10/min) exists for unkeyed agent browsing.
2Retrieval. The question is embedded and matched against the pillar-scoped corpus in Postgres (pgvector / halfvec). Faculty-approved interpretations are weighted above raw paper chunks so steward edits actually move what the model sees.
3Structured generation. Anthropic Claude is constrained to emit a fixed labeled schema — ANSWER · CITATION · PAPER · FINDING · INTERPRETATION · ACTION · INSIGHT (plus an optional CLARIFY and, on the governed path, an optional ADVISOR_NOTE) — alongside two refusal tokens (REFUSE: off-topic, UNCOVERED: in-scope but not in corpus). Refusal is an output token, not a soft instruction in prose.
4Citation guard. After streaming, verifyCitation() in the api-server's lib/rag.ts parses the CITATION: line, extracts first-author surname + year, and checks at least one retrieved provenance entry matches. Result (verified / unmatched / missing) ships to the client in the SSE done event so the UI can suppress sources on a hallucinated cite.
5Steward queue. Uncovered questions and new interpretation drafts land in the named pillar steward's console (/api/faculty/*, /api/faculty/interpretations/*). The steward edits, the row transitions proposed → approved, the body is re-embedded into interpretation_chunks, and the next matching question starts pulling the faculty voice.
6Signed response out. The answer is returned with a queryable receipt: question → retrieved chunks → source → approving faculty member → timestamp + version, all in SQL (agent_queries joined to interpretations and sources).

Why it's good

The output is auditable, not just fluent. Seven labeled sections are the model's contract, so every conforming answer is deterministically parseable by partners and reviewable by stewards. The citation guard catches drift from the contract post-hoc and the UI degrades safely when a section is missing or unmatched.
Refusal is in code, not prompted prose. REFUSE: (off-topic) and UNCOVERED: (in-scope but ungrounded) are output tokens with their own client-side handling and steward-inbox plumbing — not a "please refuse" line in a system prompt.
Citations are verified, not promised. The citation guard parses the model's claim and matches it against the chunks that were actually retrieved. Hallucinated surnames or years are logged with the queryId, and the verification result is shipped to the client so the UI can suppress the source strip on an unmatched cite.
Faculty-in-the-loop is a real workflow. Steward queue, draft → proposed → approved transitions, versioned snapshots in interpretation_versions, edit history, and a steward insights endpoint that closes the loop from agent_queries back to the people writing interpretations — not a prompt trick.

How it scales · where it fails safely.

The retrieval layer, replay model, failure modes, security posture, and partner contract — described in terms of the actual tables, indexes, and code paths in production today.

Retrieval — what we actually do

Embeddings: text-embedding-3-large, stored as halfvec(3072) in Postgres with an HNSW cosine index (agent_queries_embedding_hnsw_idx) — no second vector DB to operate. Two pillar-scoped pools query in parallel — approved interpretation_chunks and raw source_chunks — with top-K=8 per side. The merge in lib/rag.ts ranks interpretation chunks above raw paper chunks tied at distance, so a steward edit immediately moves what the model sees with no re-train and no re-deploy. The corpus is curated, not crawled.

Reproducibility — every answer is replayable

Every row in agent_queries stores the question, question_embedding (halfvec(3072)), embedding_model, the pillar_ids, retrieved_source_ids[], retrieved_interpretation_ids[], top_score, was_uncovered, latency_ms, answer_text, and created_at. Combined with the immutable interpretation_versions table (every approved edit snapshotted) and the answering model pin (claude-sonnet-4-6), any past answer can be re-run, audited, and diffed against the current state of the corpus.

Security & data posture

Consumer query rows are PII-free — only an opaque session_id (random UUID in an httpOnly cookie, never linked to an account) is stored on agent_queries; no email, no IP, no user-agent on the answer log. Pageview analytics on the same surface capture IP and user-agent in a separate table for traffic measurement only, deletable on partner / data-residency request. Faculty console is gated by Clerk with role-scoped sessions and a platform-admin flag in faculty_users. Partner API keys are stored as hashes only (partner_keys.key_hash, unique) with the prefix kept for human matching, and are revocable per-key via revoked_at. All traffic is TLS; Postgres is encrypted at rest by the managed provider.
