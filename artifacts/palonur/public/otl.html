The one promise behind everything below

Raw research data is never used to train any AI model. It lives in a governed database, and Stanford's material is intended to sit on Stanford's own servers. To answer a question, only the excerpts needed for that one answer are sent to the AI to draft a reply — used for that single answer, never to train it.

Question 1AI architecture
Question 1

What is the AI architecture?

Summary

Palonur is built to behave like a careful librarian, not a know-it-all. A normal chatbot answers from memory and can confidently make things up. Palonur does not. For every question it first looks up faculty-approved material, then writes its answer using only what it found, and attaches the citation. If it cannot find approved material, it says so plainly instead of guessing.

The AI is a writer, not the source of truth. The source of truth is the faculty-approved library behind it.

Technical detail

The system is a governed Retrieval-Augmented Generation (RAG) pipeline. The components are:

  • Knowledge layer — faculty-approved sources and steward-written interpretations, chunked and embedded in-house by a self-hosted open-source model (gte-small, 384-dim) running in our own process — the approved text is never sent to a third-party embedding service — stored as halfvec in PostgreSQL/pgvector with an HNSW cosine index.
  • Retrieval — per-question vector search over approved-only chunks; steward interpretations are weighted above raw paper excerpts.
  • Generation — Anthropic Claude, called as a service through the Replit AI Integrations proxy, constrained to emit labeled sections (answer, citation, paper, finding, interpretation).
  • Guards — an observe-only citation guard verifies the cited author/year actually exists in the retrieved set; a voice guard checks tone. Two refusal modes (REFUSE for off-topic, UNCOVERED for "not in the approved corpus").

No model is trained, fine-tuned, or adapted on our data anywhere in the system — the LLM is used purely for inference.

Question 2Full data flow
Question 2

What is the full data flow?

Summary

There are two journeys. First, knowledge gets in: a faculty steward reviews material and approves it before anything becomes answerable — nothing unapproved is ever reachable. Second, a question gets answered: the question comes in, the system looks up approved material, the AI drafts an answer from that material, an automatic check compares the citation against the retrieved sources and flags any mismatch, and the answer streams back. Raw material never goes to the AI in bulk, and never trains it.

Technical detail

Two pipelines, both shown below. Ingestion is human-gated: nothing is retrievable until status = 'approved'; approval records the approver, timestamp, version, and a content snapshot, and the approved chunk text is embedded in-house by a self-hosted model to produce the stored vectors — it is never sent to a third-party embedding service. Query is per-request: only the top-k approved excerpts are assembled into the context for a single Claude inference. Answers stream over Server-Sent Events; a post-stream observe-only guard checks the citation against the retrieved set and flags (never rewrites) any mismatch.

The core guaranteeRaw data is protected & never trained on

Where the data lives, and what crosses the line.

This is the picture to keep in mind. The research material — the curated corpus of approved sources and steward interpretations, not user or patient data — sits inside a governed environment; for Stanford's material, that environment is intended to live on Stanford's own servers. Approved text is turned into search vectors in-house, by an open-source model we run ourselves — that step never leaves the governed environment. The only outside service we call is the one that drafts a single answer, and only the handful of excerpts for that one question ever reach it. We never run it on the material in bulk and never let it train on the material.

Text crosses the boundary only once, and only for inference: the handful of approved excerpts needed to draft a single answer, per question. Embeddings are computed in-house and never leave the governed environment. No AI model is ever trained or fine-tuned on the material; retention of those per-answer excerpts is governed by the provider's API terms (see note below).

What never happens
  • No model is trained or fine-tuned on the research corpus — ever.
  • The corpus is never sold, published, or handed to a provider to train on.
  • Under the provider's API terms (to be confirmed contractually), the model provider does not train on our inputs or outputs.
  • Embeddings are numeric vectors, not a human-readable copy of the text.
What always happens
  • A human steward approves material before it can be used.
  • Every published answer carries a verifiable citation.
  • Approvals are recorded and timestamped — a full audit trail.
  • At query time, only the minimum excerpts for one answer are sent to the model.

Question 3Security & privacy governance
Question 3

How are security and privacy governed?

Summary

Three ideas. Only the right people can see or change things — faculty review their own pillar, admins run the platform, and roles don't overlap. We collect as little personal information as possible, and we never store anything sensitive in plain form. Every published answer has a named human behind it, recorded and timestamped, so nothing is anonymous or unaccountable.

Technical detail
  • Authentication — faculty via Clerk (institutional SSO-capable); editors/investors via single-use magic links → short-lived signed session cookies; admin behind a separate scoped gate.
  • Authorization — least privilege; write routes enforce steward/role membership in middleware; retrieval is hard-gated to status='approved'.
  • Privacy / PII — minimal collection; consent captured with timestamp; IP stored only as a salted SHA-256 hash, never raw.
  • Secrets — held in the platform secret store / deployment secrets, never in code or the client bundle.
  • Abuse controls — per-IP rate limits and concurrency caps on public endpoints.
  • Integrity — observe-only citation/voice guards plus structured logging; approvals signed and versioned.

Privacy and security are enforced in the code paths themselves (gated queries, hashed identifiers, role middleware), not just in policy.

Question 4How the user interacts
Question 4

How does a user interact with the system?

Summary

A reader types a health question and gets a clear, sourced answer — with the study and the faculty interpretation shown alongside it, not buried. Behind the scenes, a Stanford faculty steward uses a private portal to review and approve what the system is allowed to say, and to set the voice it answers in. Outside platforms can also plug in through a controlled connection. The faculty member is always in the loop.

Technical detail
  • Consumer — asks at the public answer surface; the structured sections render as distinct UI (answer, citation, source, interpretation); responses stream live.
  • Embeddable widget — a white-label "ask" box an outside expert drops on their own site, hard-locked to one pillar.
  • Faculty steward — Clerk-authenticated portal: review/approve queue, reliability rubric, and voice profile.
  • Partner / AI platform — metered API keys with rate tiers.
  • Admin — internal operations surfaces, separately gated.

Question 5Hosting
Question 5

Who is hosting it?

Summary

For development and review, it currently runs on a managed cloud (AWS, US West) with a managed PostgreSQL database. The model that drafts answers is called as a service from Anthropic (Claude); the model that turns approved text into search vectors runs in-house. This is a development setup only — all Stanford material should be hosted on Stanford's own servers, inside Stanford's environment. The system is built from standard, portable parts, so it deploys there without changes.

Technical detail
  • Development / review (current) — managed cloud (AWS, US West) for the API + web apps, with managed PostgreSQL (pgvector) and object storage; answer model via the Anthropic API, embeddings computed in-house (self-hosted open-source model).
  • Portable by design — runs in any environment offering Node.js, PostgreSQL with pgvector, object storage, and outbound HTTPS to the model APIs. No proprietary lock-in.
  • Production for Stanford material — deploy into a Stanford-controlled cloud/VPC with Stanford-managed Postgres, so the stored corpus stays within Stanford's boundary; the answer model is still called per question, under contractually agreed no-training / retention terms.

Ownership & commercial modelIP, distribution, and revenue

Who owns what, and how this is offered.

Palonur does not own the research or the data, and is not seeking an IP license. The underlying material remains Stanford's. Palonur builds and operates the governed access layer and offers convenient, cited access to it — we sell access and convenience, never the data itself.

Ownership
  • The research corpus and underlying data remain Stanford's; Palonur never takes ownership.
  • No IP license is required — Palonur licenses nothing from Stanford and claims no rights in the material.
  • Palonur owns only the software that retrieves and presents the approved material.
Distribution & revenue
  • Offered to users of Stanford Lifestyle Medicine programs as a freemium service — a free tier, plus a paid tier for fuller access.
  • We propose to share a portion of revenue with Stanford.
  • We also propose to direct funds toward establishing a Stanford Lifestyle Medicine Institute.

The commercial relationship is access-and-revenue, not a transfer of data or IP. Exact revenue terms and the Institute structure are proposals we would shape together with Stanford.

ReferenceGlossary & next steps

A short glossary, and where we'd value OTL's guidance.

Plain-language glossary
RAG
"Retrieval-Augmented Generation" — the AI looks up approved material first, then writes from it. It is not answering from memory.
Inference
Using a trained model to produce one answer. The opposite of training — nothing about the model changes.
Embedding / vector
A list of numbers that represents the meaning of a passage so similar text can be found. Not a human-readable copy.
Steward
The named faculty member who reviews and approves what the system may say for their pillar.
Pillar
A subject area (e.g. Sleep), each governed by its own steward.
Trust boundary
The line between the governed environment (the curated research corpus + steward interpretations) and the outside model service. Only minimal excerpts cross it, per answer.
Where we'd value OTL's guidance
  • The preferred hosting boundary for Stanford data (managed cloud vs. Stanford-controlled environment).
  • The exact provider terms (no-training / zero-retention / BAA) Stanford wants reflected.
  • Any additional security or privacy review steps to fold into the steward workflow.

Governance & accountabilityWho stands behind every answer

Who decides what the system may say — and who answers for it.

Every answer traces to a named Stanford faculty steward's approval. This page states plainly where authority comes from, what the system is allowed to claim, how information is controlled, and who is accountable when it speaks.

Authority source
  • Named faculty stewards are the sole source of authority: nothing is served unless a steward approved both the source and the interpretation of it.
  • Approval is recorded per item — who approved it, and when — and is revocable; unapproved or retired material drops out of retrieval immediately.
  • Palonur engineering has no editorial override: the company cannot add or alter claims.
Allowed claims
  • The system may state only what appears in steward-approved material; each covered answer carries a citation to the underlying work.
  • A citation guard checks every cited answer against the retrieved provenance; an unverifiable citation is flagged and its source strip is suppressed.
  • Outside the approved corpus the system says so plainly or refuses — it never improvises an answer.
Information control
  • The governed corpus lives in Palonur's database; only the minimal excerpts needed for one answer cross to the model provider, under no-training inference terms.
  • Private surfaces — this brief, the dashboards — are gated on the server, and the gates fail closed when unconfigured.
  • User data is never sold and never used to train models.
Accountability
  • Every question, answer, citation-check outcome, and steward approval is logged, so any answer can be reconstructed after the fact.
  • Access to governance surfaces is audited — including who opened this brief, and when.
  • A named human answers for each layer: the steward for content, Palonur for operating the platform — karan@palonur.com.

This statement is mirrored as a live Governance view in Palonur's internal admin console, so what we state here matches what operators see day to day.

For Stanford Medicine IT's governance and security review, the claims summarized in this brief are backed by a structured written package maintained alongside the codebase. Request it from karan@palonur.com.

What the package contains
  • Threat model — assets, trust boundaries, STRIDE-style threats, mitigations with code-level pointers, and an honest accepted-risks list.
  • Data-flow inventory, per surface — every external provider that receives user or research data, what crosses, and when. The asklifestylemedicine.com answer path is documented separately: in-house embeddings and Anthropic Claude only.
  • Compliance posture — no SOC 2 today; infrastructure attestations inherited via Replit on AWS; application controls documented in the package, structured to answer a HECVAT Lite questionnaire.
  • One-page posture summary — authentication, authorization, audit logging, secrets, prompt-injection defenses, and named remediation items.
Honest by design
  • Known gaps are listed as gaps — shared-password admin, in-memory rate limits, and the observe-only advice guard are documented, not glossed over.
  • The same honest-claims rules as this brief apply: provider no-training is a contractual posture, and no zero-retention or "corpus never leaves" claims are made.
  • Every claim in the package points at the file in the codebase that implements it.

Package files: threat_model.md, data-flow-inventory.md, compliance-posture.md, security-posture-summary.md — kept in the repository so the code and its review documents cannot drift apart.
